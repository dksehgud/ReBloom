# Backend Experience Draft

## 최신 반영: 실제 AWS EKS/RDS 검증 결과

백엔드 직무 자기소개서에서는 커넥션 풀 개선 경험을 Docker 시뮬레이션보다 실제 AWS 검증 결과 중심으로 쓰는 것이 더 설득력 있다.

핵심 수치:

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 환경 | EKS + RDS PostgreSQL | EKS + RDS PostgreSQL |
| 서비스 | `report-service` | `report-service` |
| 파드 수 | 3 | 3 |
| 파드당 HikariCP max pool | 20 | 8 |
| 이론상 최대 DB 연결 | 60 | 24 |
| RDS `max_connections` | 40 | 40 |
| Ready 파드 | 2 / 3 | 3 / 3 |
| CrashLoopBackOff | 발생 | 0 |
| DB 모니터링 쿼리 | 슬롯 부족으로 실패 | 성공 |
| 실제 JDBC 세션 | 포화 상태 | 24 |
| CloudWatch `DatabaseConnections` | 최대 31 | 24 |

자기소개서용 문장:

EKS 기반 MSA 환경에서 파드 수가 늘어날 때 각 파드의 HikariCP 커넥션 풀이 누적되어 DB 연결 슬롯을 고갈시킬 수 있다고 판단했습니다. 이를 검증하기 위해 `max_connections=40`으로 제한한 RDS PostgreSQL과 EKS 클러스터를 직접 구성하고, 실제 `report-service` 파드 3개를 배포했습니다. 개선 전에는 파드당 풀 크기 20으로 최대 60개의 DB 연결을 시도할 수 있었고, 배포 결과 일부 파드가 `remaining connection slots are reserved` 오류로 실패했습니다. CloudWatch `DatabaseConnections`는 실제 열린 연결 기준 최대 31개를 기록했고, DB 모니터링 쿼리도 슬롯 부족으로 실패했습니다. 이후 파드당 풀 크기를 8로 제한해 최대 연결 예산을 24개로 낮췄고, 동일한 3개 파드가 모두 Ready 상태로 올라오는 것을 확인했습니다. PostgreSQL `pg_stat_activity`에서도 실제 애플리케이션 JDBC 세션이 24개로 확인되어, 파드 증가 시 발생할 수 있는 DB 연결 고갈 위험을 운영 지표 기반으로 줄였습니다.

## 2번. 개발 환경 및 FE 테스트 게이트 정리

이 항목은 백엔드 직무 자소서의 메인 경험으로 쓰기보다는, 프로젝트를 마무리하며 테스트와 협업 환경을 정리한 보조 경험으로 쓰는 것이 적절하다.

### 개선 이유

프로젝트 폴더명이 변경된 뒤 `FE/web/node_modules` 내부의 pnpm Junction이 예전 경로를 가리키고 있었다. 이 때문에 로컬에서 `vitest` 실행 파일은 보이지만 실제 패키지 경로를 따라가면 이전 폴더를 참조해 테스트 실행이 실패할 수 있는 상태였다.

또한 기존 FE CI는 `npm ci` 이후 바로 `npm run build`만 수행했다. 즉, 테스트가 실패하는 코드가 있어도 빌드만 통과하면 배포 산출물이 만들어질 수 있었다. 백엔드 중심 개선은 아니지만, 프로젝트 품질 관리 관점에서는 테스트가 빌드 전에 실행되도록 만드는 것이 필요했다.

### 기존 문제

- `node_modules`가 폴더명 변경 전 경로를 참조해 로컬 테스트 실행이 불안정했다.
- FE CI가 빌드만 수행하고 테스트를 실행하지 않았다.
- 테스트 환경에서 `import.meta.env.VITE_API_BASE_URL` 값이 없으면 API base URL 관련 코드가 환경에 따라 흔들릴 수 있었다.
- 결과적으로 로컬 환경과 CI 환경의 테스트 재현성이 떨어질 수 있었다.

### 어떻게 바꿨는지

- `Infra/setting/.gitlab-ci-fe.yml`에서 FE 빌드 전에 `npm run test`를 실행하도록 추가했다.
- `FE/web/vite.config.ts`에서 `mode === 'test'`일 때 `import.meta.env.VITE_API_BASE_URL` 기본값을 `http://localhost:8080`으로 주도록 설정했다.
- 이 변경으로 테스트 환경에서 API base URL이 명확해지고, 빌드 전에 FE 테스트가 먼저 실행되는 흐름을 만들었다.

### 전후 비교

| 구분 | 개선 전 | 개선 후 |
| --- | --- | --- |
| FE CI 흐름 | `npm ci` 후 바로 `npm run build` | `npm ci` 후 `npm run test`, 이후 `npm run build` |
| 테스트 환경 API URL | 환경변수 누락 시 테스트가 흔들릴 수 있음 | test mode 기본값 제공 |
| 품질 게이트 | 빌드 통과 중심 | 테스트 통과 후 빌드 |

### 자소서에서 쓸 수 있는 형태

프로젝트 마무리 단계에서 빌드만 수행하던 FE CI 흐름이 테스트 실패를 사전에 차단하지 못한다는 점을 확인했습니다. 또한 폴더명 변경 이후 로컬 `node_modules`의 pnpm Junction이 이전 경로를 참조해 테스트 실행 재현성이 떨어지는 문제도 발견했습니다. 이를 계기로 FE CI에 `npm run test`를 빌드 전에 추가하고, Vitest 실행 시 필요한 API base URL 기본값을 Vite 설정에 명시했습니다. 이 경험은 핵심 백엔드 성능 개선은 아니지만, 배포 전 테스트 게이트를 추가해 프로젝트 품질 관리 흐름을 보강한 작업이었습니다.

### 주의해서 말할 점

이 경험은 백엔드 지원에서 메인으로 내세우기에는 약하다. 면접이나 포트폴리오에서는 "프론트 개선"이 아니라 "테스트와 CI 품질 게이트를 보강한 보조 경험" 정도로 짧게 언급하는 것이 좋다.

## 4번. 자소서용 백엔드 개선 경험

아래 두 가지를 메인 경험으로 잡는 것이 가장 좋다.

1. 리포트 조회 성능 병목을 재현하고 인덱스로 개선한 경험
2. EKS 파드 증가 시 DB 커넥션 고갈 위험을 재현하고 풀 크기를 제한한 경험

## 경험 1. 대용량 리포트 조회 성능 개선

### 개선 이유

`report-service`는 보호자와 상담사가 아이의 관찰 기록을 날짜 범위로 조회하는 기능을 담당한다. 이 조회는 서비스 사용량이 늘어날수록 반복적으로 호출될 가능성이 높고, 데이터가 누적될수록 성능 병목이 되기 쉬운 경로였다.

기존 테이블에는 조회 조건인 `children_id`, `report_date` 조합을 직접 지원하는 인덱스가 없었다. 그래서 데이터가 많아졌을 때 DB가 필요한 범위만 빠르게 찾지 못하고 전체 테이블을 훑는 방식으로 실행될 가능성이 있었다.

### 기존 문제

- 날짜 범위 조회가 반복되는 핵심 경로였지만 조회 패턴에 맞는 복합 인덱스가 없었다.
- Docker PostgreSQL에 365,000건의 더미 데이터를 넣고 확인한 결과, 기존 실행 계획은 `Parallel Seq Scan`이었다.
- 즉, 조건에 맞는 일부 리포트만 필요해도 테이블을 넓게 스캔하는 구조였다.
- 벤치마크 결과 p95 응답 시간이 `41.292ms`까지 측정됐다.

### 어떻게 바꿨는지

- 실제 조회 조건을 기준으로 `children_id`, `report_date` 중심의 복합 인덱스를 추가했다.
- Flyway 마이그레이션으로 `V9__add_report_query_indexes.sql`을 작성해 운영 DB에도 동일하게 반영 가능하도록 했다.
- 단순히 인덱스를 감으로 추가하지 않고, Docker PostgreSQL에서 더미 데이터를 생성한 뒤 `EXPLAIN ANALYZE`와 반복 벤치마크로 전후를 비교했다.

### 전후 비교

| 구분 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 실행 계획 | `Parallel Seq Scan` | `Bitmap Index Scan` |
| 단일 실행 시간 | `22.412ms` | `0.140ms` |
| 평균 응답 시간 | `35.188ms` | `0.137ms` |
| p95 응답 시간 | `41.292ms` | `0.309ms` |
| p95 개선율 | - | 약 `99.3%` 감소 |

### 자소서 문장

프로젝트 후반부에 데이터가 누적될수록 리포트 조회가 병목이 될 수 있다고 판단했습니다. `report-service`의 날짜 범위 조회는 `children_id`와 `report_date` 조건을 반복적으로 사용했지만, 기존 스키마에는 해당 조회 패턴을 직접 지원하는 복합 인덱스가 없었습니다. 이를 확인하기 위해 Docker PostgreSQL 환경에 365,000건의 더미 데이터를 구성하고 `EXPLAIN ANALYZE`로 실행 계획을 분석했습니다.

분석 결과 기존 조회는 `Parallel Seq Scan`으로 테이블을 넓게 스캔하고 있었고, 반복 벤치마크에서 p95 응답 시간이 41.292ms로 측정되었습니다. 이후 조회 조건에 맞춘 복합 인덱스를 Flyway 마이그레이션으로 추가했고, 실행 계획이 `Bitmap Index Scan`으로 전환되었습니다. 그 결과 p95 응답 시간은 0.309ms로 감소해 약 99.3%의 성능 개선을 확인했습니다. 이 과정에서 단순히 인덱스를 추가하는 데 그치지 않고, 더미 데이터 생성, 실행 계획 분석, 전후 지표 비교를 통해 개선 효과를 검증했습니다.

### 면접에서 강조할 점

- "실제 서비스에서 자주 호출될 조회 경로를 먼저 찾았다."
- "인덱스를 추측으로 넣지 않고 데이터와 실행 계획으로 확인했다."
- "평균값만 보지 않고 p95를 사용해 사용자 체감 지연을 기준으로 비교했다."
- "Flyway 마이그레이션으로 운영 반영 가능성을 고려했다."

## 경험 2. EKS 환경의 DB 커넥션 고갈 위험 개선

### 개선 이유

MSA 구조에서는 서비스별로 DB 커넥션 풀이 따로 생긴다. 로컬이나 단일 인스턴스에서는 문제가 잘 보이지 않지만, EKS에서 파드 수가 늘어나거나 rolling update 중 새 파드가 추가되면 각 파드의 HikariCP 풀이 동시에 DB 연결을 확보하려고 한다.

DB의 `max_connections`는 제한되어 있는데, 애플리케이션 파드 수와 커넥션 풀 크기를 계산하지 않으면 사용자가 갑자기 많아졌을 때가 아니라 배포나 스케일아웃만으로도 DB 연결 슬롯을 초과할 수 있다.

### 기존 문제

- DB를 사용하는 서비스들의 HikariCP 최대 풀 크기가 운영 환경 기준으로 명확히 제한되어 있지 않았다.
- 파드가 여러 개로 늘어났을 때 전체 DB 연결 수가 얼마까지 증가하는지 계산하기 어려웠다.
- 예를 들어 파드 3개가 각각 커넥션 풀 20개를 가지면 이론상 최대 60개 연결을 시도한다.
- Docker PostgreSQL에서 `max_connections=40` 조건으로 재현했을 때, 실제 사용 가능한 연결 슬롯은 37개였고 60개 연결 시도 중 23개가 실패했다.

### 어떻게 바꿨는지

- DB 사용 서비스 4개에 HikariCP 설정을 명시했다.
- EKS deployment에 `DB_POOL_MAX_SIZE`, `DB_POOL_MIN_IDLE`, `DB_POOL_CONNECTION_TIMEOUT_MS`, `DB_POOL_VALIDATION_TIMEOUT_MS` 환경변수를 추가했다.
- 파드당 최대 풀 크기를 8로 제한해 파드 3개 기준 최대 연결 시도를 24개로 낮췄다.
- Docker PostgreSQL에서 같은 조건으로 다시 검증해 연결 실패율이 0%가 되는지 확인했다.

### 전후 비교

| 구분 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 가정한 파드 수 | 3개 | 3개 |
| 파드당 풀 크기 | 20 | 8 |
| 최대 연결 시도 | 60 | 24 |
| 성공 연결 | 37 | 24 |
| 실패 연결 | 23 | 0 |
| 실패율 | `38.3%` | `0%` |
| DB 사용 서비스 설정 범위 | 0 / 4 | 4 / 4 |

### 자소서 문장

EKS 기반 MSA 환경에서 파드 수가 증가할 때 DB 커넥션 풀이 누적되어 장애로 이어질 수 있다고 판단했습니다. 기존에는 DB를 사용하는 서비스들의 HikariCP 풀 크기가 운영 환경 기준으로 명확히 제한되어 있지 않아, 파드가 늘어나거나 rolling update 중 임시 파드가 추가될 경우 전체 DB 연결 수가 DB의 최대 연결 수를 초과할 수 있었습니다.

이를 검증하기 위해 Docker PostgreSQL에서 `max_connections=40` 조건을 구성하고, 파드 3개가 각각 20개의 커넥션 풀을 가지는 상황을 재현했습니다. 그 결과 60개 연결 시도 중 23개가 실패해 38.3%의 실패율이 발생했습니다. 이후 DB 사용 서비스 4개에 HikariCP 풀 상한을 환경변수로 명시하고, 파드당 최대 풀 크기를 8로 제한했습니다. 동일 조건에서 최대 연결 시도는 24개로 줄었고, 연결 실패율은 0%로 감소했습니다.

이 개선을 통해 단순히 동시 접속자 수만 보는 것이 아니라, EKS 파드 수와 서비스별 커넥션 풀, DB 최대 연결 수를 함께 고려해 운영 안정성을 설계하는 경험을 쌓았습니다.

### 면접에서 강조할 점

- "동시 접속자 수와 DB 커넥션 수는 1:1 관계가 아니다."
- "문제는 사용자 30명이 바로 DB 연결 30개를 점유한다는 뜻이 아니라, 파드별 커넥션 풀이 누적될 수 있다는 점이다."
- "파드 수, rolling update, maxSurge, HikariCP pool size, DB max_connections를 함께 계산해야 한다."
- "Docker PostgreSQL로 제한된 연결 슬롯을 만들고 실제 실패율을 측정했다."

## 최종 추천 자소서 구성

### 600자 내외

프로젝트 후반부에 데이터 증가와 운영 환경 확장을 고려해 백엔드 병목을 점검했습니다. 먼저 `report-service`의 날짜 범위 조회가 `children_id`, `report_date` 조건을 반복 사용하지만 해당 패턴을 지원하는 복합 인덱스가 없다는 점을 발견했습니다. Docker PostgreSQL에 365,000건의 더미 데이터를 구성하고 `EXPLAIN ANALYZE`로 확인한 결과, 기존 조회는 `Parallel Seq Scan`으로 수행되었고 p95 응답 시간이 41.292ms였습니다. 이후 조회 조건에 맞춘 복합 인덱스를 Flyway 마이그레이션으로 추가해 실행 계획을 `Bitmap Index Scan`으로 전환했고, p95 응답 시간을 0.309ms로 약 99.3% 개선했습니다. 또한 EKS 환경에서 파드 수 증가 시 HikariCP 커넥션풀이 누적되어 DB 연결 슬롯을 초과할 수 있음을 Docker PostgreSQL로 재현했습니다. 파드 3개, 풀 크기 20 조건에서 60개 연결 시도 중 23개가 실패했으나, 서비스별 풀 크기를 8로 제한해 동일 조건의 실패율을 38.3%에서 0%로 낮췄습니다.

### 한 줄 요약

Docker PostgreSQL 더미 데이터와 제한된 DB 연결 환경을 직접 구성해 조회 성능 병목과 EKS 파드 증가 시 커넥션 고갈 위험을 재현했고, 인덱스와 HikariCP 풀 제한을 적용해 p95 응답 시간을 99.3% 개선하고 연결 실패율을 38.3%에서 0%로 낮췄습니다.
